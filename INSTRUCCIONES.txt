LECTURACLUB - GUIA PASO A PASO
==============================

Esta guia explica como ejecutar LecturaClub en tu computadora, activar el correo,
iniciar sesion como superadministrador y, si lo deseas, preparar el despliegue en
un servidor. La aplicacion no se publica en Internet por el solo hecho de subir
el codigo a GitHub.

1. ABRIR LA CARPETA DEL PROYECTO
-------------------------------

Abre la carpeta donde se guardo el proyecto. En Windows, puedes abrir
PowerShell desde la barra de direcciones del Explorador de archivos. Ejecuta
los comandos de esta guia desde esa carpeta, donde estan package.json y
server.js.

2. COMPROBAR E INSTALAR NODE.JS
------------------------------

Ejecuta:

node --version
npm --version

El proyecto requiere Node.js 22.13 o posterior porque utiliza la base de datos
SQLite integrada en Node. Si el primer comando falla o muestra una version
anterior, instala una version reciente de Node.js y abre una terminal nueva.

3. INSTALAR DEPENDENCIAS
------------------------

En PowerShell, dentro de la carpeta del proyecto, ejecuta:

npm install

Esto instala las dependencias necesarias. Normalmente solo se hace la primera
vez, o cuando cambian las dependencias del proyecto.

4. PREPARAR LA CONFIGURACION LOCAL
---------------------------------

El archivo .env contiene configuracion privada y no se publica en GitHub.
Para crearlo desde la plantilla, ejecuta:

if (-not (Test-Path .env)) { Copy-Item .env.example .env } else { Write-Host "Ya existe .env; no se modifico." }

Abre el archivo para editarlo:

notepad .env

Guarda el archivo con el nombre exacto ".env", no ".env.txt". No compartas ni
subas ese archivo: puede contener contrasenas.

La configuracion local de la aplicacion utiliza:

NODE_ENV=development
PORT=3000
BASE_URL=http://localhost:3000

La plantilla ya contiene los valores locales. No es necesario cambiar REQUEST_HASH_SECRET
para ejecutar la aplicacion en tu computadora. Ese secreto si es obligatorio en produccion.

5. CONFIGURAR EL CORREO CON GMAIL (OPCIONAL, PERO NECESARIO PARA EMAIL)
----------------------------------------------------------------------

El servidor utiliza el correo para confirmar registros y enviar enlaces de
recuperacion de contrasena. Para empezar con poco volumen puedes configurar una
cuenta Gmail como remitente:

a. Activa la verificacion en dos pasos de la cuenta Google remitente.
b. Crea una contrasena de aplicacion desde:
   https://myaccount.google.com/apppasswords
c. En .env, completa estas lineas con tu direccion de Gmail:

SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=tu-cuenta@gmail.com
SMTP_PASSWORD=la-contrasena-de-aplicacion-de-Google
SMTP_FROM=tu-cuenta@gmail.com

Usa una contrasena de aplicacion, no la contrasena habitual de Google. Si Google
no muestra la opcion de generar contrasenas de aplicacion, no pongas tu
contrasena normal: revisa los requisitos de Google o elige otro proveedor SMTP.
Gmail tiene limites de envio y la disponibilidad depende de la cuenta.

Si SMTP o BASE_URL no estan configurados correctamente, no se podran crear
nuevas cuentas verificadas ni enviar recuperaciones por correo. Los registros
reciben un codigo de seis digitos que caduca en 10 minutos; las solicitudes y
los intentos estan limitados. El codigo se escribe en la pagina para activar
la cuenta. Los enlaces para restablecer contrasenas caducan a los 30 minutos.
Revisa tambien la carpeta de correo no deseado.

La comprobacion de los registros MX del dominio ayuda a rechazar dominios sin
servicio de correo, pero no demuestra que un buzon individual exista. Abrir el
enlace recibido confirma que la persona puede acceder a ese buzon.

6. CUENTA DE SUPERADMINISTRADOR
-------------------------------

Para crear el primer superadministrador, configura ADMIN_EMAIL y
ADMIN_PASSWORD en .env. ADMIN_PASSWORD debe tener al menos 12 caracteres.
ADMIN_NAME y ADMIN_USERNAME son opcionales; si no se indican, se utilizan
valores derivados del correo. Al iniciar, el servidor crea la cuenta verificada
si el correo no existe. Si ese correo ya pertenece a un usuario que no es
superadministrador, el servidor no inicia: configura otro correo. Si la cuenta
ya existe, cambiar ADMIN_PASSWORD no cambia su contrasena.

Inicia sesion con el correo o el nombre de usuario y la contrasena configurada.
El panel "Usuarios" permite listar cuentas, cambiar el rol entre profesor y
alumno, crear cuentas, bloquear o desbloquear el acceso, cerrar sesiones,
eliminar cuentas y restaurarlas sin perder su progreso. El panel no permite
cambiar el rol de un superadministrador, eliminar la propia cuenta ni eliminar
el ultimo superadministrador. Guarda las credenciales fuera del repositorio y
no incluyas datos reales en esta guia.

El registro publico solo permite crear cuentas de alumno o profesor; no permite
registrar superadministradores.

7. REGLAS DE NOMBRE Y CONTRASENA
-------------------------------

En el campo "Nombre completo" del registro solo se aceptan letras (incluidas
letras acentuadas), espacios, apostrofes y guiones. No se aceptan numeros. El
nombre de usuario es un campo distinto y puede contener numeros.

Las contrasenas nuevas, tanto al registrarse como al restablecer una contrasena,
deben:

- Tener entre 10 y 128 caracteres.
- Incluir al menos una letra mayuscula.
- Incluir al menos una letra minuscula.
- Incluir al menos un numero.
- Incluir al menos un caracter especial, como !, *, # o @.

El servidor verifica estas reglas aunque se intente enviar un formulario sin
usar la pagina web.

8. CONTRASENAS Y ACCESO DESDE OTROS DISPOSITIVOS
------------------------------------------------

Las contrasenas se guardan usando scrypt, un algoritmo de derivacion de claves:
la base de datos almacena una sal aleatoria y un hash, no la contrasena original.
No existe ni debe existir un sistema de desencriptacion. En cada inicio de
sesion, el servidor deriva un hash de la contrasena que escribiste y lo compara
con el hash guardado.

Puedes iniciar sesion desde otro equipo o navegador usando la misma cuenta
siempre que ese dispositivo se conecte a la misma aplicacion y base de datos
del servidor. Cada navegador crea su propia sesion; no se copia automaticamente
la sesion de un dispositivo al otro. La direccion localhost solo funciona en
la computadora que ejecuta la aplicacion.

9. ACCESO A LECCIONES Y MINIJUEGOS SEGUN LA SESION
--------------------------------------------------

El superadministrador y el profesor tienen acceso completo a las lecciones y
al Arcade. Un visitante sin sesion puede navegar y practicar lecciones, pero el
progreso que envia la API requiere autenticacion. El cliente muestra el Arcade
a usuarios autenticados; sus niveles para alumnos se desbloquean en orden. Los
controles de la pagina no sustituyen la autorizacion del servidor: este tambien
valida la sesion, el rol, el alumno o juego relacionado y el orden del progreso.

El profesor y el superadministrador pueden entrar y salir de la vista de un
alumno desde el panel Avances. Esta vista es temporal y no guarda el progreso
de prueba. El backend devuelve el perfil, las lecciones, los juegos y el progreso
del alumno seleccionado; la simulacion se ejecuta en el navegador.

El servidor concede a los profesores acceso global a los alumnos y reportes;
no vincula las cuentas de alumno a un profesor concreto. El superadministrador
puede administrar las cuentas y el contenido de todos los profesores. Los
permisos se aplican en las rutas de la API, no solo ocultando botones.
Actualmente, las rutas de edicion y borrado de lecciones personalizadas para
profesores comprueban el rol, pero no limitan la operacion a las lecciones
creadas por ese profesor. En cambio, al borrar juegos, la API si comprueba el
profesor creador; el superadministrador puede operar globalmente. Ten en cuenta
este alcance al administrar el servicio con varios profesores.

Los reportes resumen intentos, errores, puntos, mejor resultado, estrellas de
la primera vez y de los reintentos, porcentaje ponderado por seccion y ranking
de lecciones mas repetidas. La vista de alumno presenta un mapa y un progreso
visual; el detalle de reportes esta en el panel docente.

Una leccion normal se presenta en tres pasos: descubrir el sonido (tocar letra
o silabas), escuchar y clasificar ejemplos (o escuchar una lectura), y practica
guiada con opciones. Cada paso habilita el siguiente al completar su actividad.
Los errores reducen las estrellas hasta un minimo de cero. Las lecciones
completadas registran intentos y resultados; el servidor asigna las recompensas
de XP y controla el orden de las lecciones del catalogo. Los desafios de repaso
tienen una recompensa distinta de las lecciones normales.

La voz usa SpeechSynthesis del navegador en espanol y puede activarse o
desactivarse desde la interfaz; sonidos cortos y confeti usan APIs del navegador.
La disponibilidad y la voz concreta dependen del equipo y navegador. En las
lecciones de lectura, el cliente habilita continuar al pulsar el boton para
escuchar; no espera a confirmar que la locucion haya terminado.

Al crear lecciones se puede elegir una subseccion para consonantes y silabas.
Las lecciones de palabras incluyen filtros de dificultad, numero de silabas,
posicion del sonido objetivo y estructura. El profesor y el superadministrador
pueden editar lecciones asignadas y lecciones del catalogo.

El catalogo incluye vocales, consonantes, desafios de repaso y contenido de
lectura/segmentacion. Aparte de editar el catalogo, los docentes pueden asignar
lecciones personalizadas a un alumno con palabras, emojis, objetivo, tema,
filtros y posicion en el mapa. El servidor comprueba que una leccion
personalizada que se completa esta asignada al alumno autenticado, pero no la
coloca dentro de la secuencia del catalogo.

Las palabras se ilustran seleccionando emojis en el catalogo visual, organizado
por categorias y con buscador. Al asignar una leccion se puede elegir su posicion
exacta en el recorrido del alumno: antes de una leccion del mapa o al final.

El creador de juegos incluye rompecabezas, memoria de parejas y El puente de
los bloques magicos. Al comenzar cada juego, el sistema muestra y lee en voz
alta sus instrucciones; el boton de ayuda permite repetirlas. Las imagenes,
palabras y tarjetas interactivas tambien pueden reproducirse por voz al
tocarlas. Para el puente, escribe en cada fila una palabra, su imagen y una
silaba que sea solo una parte de esa palabra. El alumno ve la palabra con ese
fragmento oculto y la completa eligiendo o arrastrando uno de los bloques con
silabas configuradas para el juego. Una respuesta incorrecta permite intentarlo
de nuevo; las opciones se toman de las silabas de las palabras del propio juego.
El servidor limita estos juegos a entre 3 y 12 elementos y no acepta que la
silaba faltante sea la palabra completa. La prueba desde el panel docente no
guarda resultados.

La API del servidor permite a cualquier alumno autenticado consultar y
completar niveles del Arcade; el cliente sigue mostrando las restricciones de
nivel y secuencia previstas para alumnos. El avance de visitantes puede
practicarse, pero no se sincroniza con la API ni queda guardado en SQLite.

Nota sobre la validacion de resultados: el servidor valida la identidad, el rol,
los identificadores, el orden y los valores declarados en la solicitud de
finalizacion. No observa cada clic o respuesta en el navegador; una solicitud
autenticada de finalizacion es la que registra el resultado.

Las cuentas de alumno se pausan tras 60 minutos de sesion durante 15 minutos,
para descansar la vista. El temporizador de descanso se conserva en
sessionStorage de esa pestana. Ademas, cualquier sesion iniciada se cierra en
el navegador tras 3 minutos sin actividad registrada (puntero, teclado,
desplazamiento, toque, escritura, cambio de controles, foco, clic o arrastrar y
soltar). El cliente comprueba cada 20 segundos si el servidor sigue reconociendo
la sesion. Este cierre por inactividad de la pagina es independiente de la
duracion de siete dias de la cookie del servidor; bloqueos, eliminaciones,
logout y cambio de contrasena tambien pueden invalidar sesiones antes.

10. INICIAR LA APLICACION E INICIAR SESION
------------------------------------------

Desde PowerShell, dentro de la carpeta del proyecto, inicia el servidor:

npm start

Cuando aparezca el mensaje de que LecturaClub esta disponible, abre esta
direccion en el navegador:

http://localhost:3000

No abras index.html directamente: el inicio de sesion, los datos y el progreso
requieren el servidor en ejecucion. Para detener el servidor, vuelve a su
ventana de PowerShell y pulsa Ctrl+C. Para iniciarlo otro dia, repite "npm
start". Para desarrollo con reinicio automatico al editar archivos, puedes
usar "npm run dev".

Si aparece un error de puerto ocupado, puede haber otro servidor usando el
puerto 3000. Detenlo con Ctrl+C en la terminal donde se inicio antes de volver
a ejecutar npm start.

11. BASE DE DATOS Y PROGRESO
----------------------------

La configuracion local DATABASE_PATH=registro.db guarda cuentas, sesiones,
progreso, codigos de verificacion, tokens de recuperacion y limites de intentos
en registro.db dentro de la carpeta del proyecto. Las contrasenas se almacenan
como hash scrypt con sal aleatoria, no como texto ni como contrasena cifrada.
La base de datos esta excluida de Git. No la borres si quieres conservar los
datos. Las tablas principales guardan:

- `users`: identidad, correo, nombre de usuario, rol, hash y sal de contrasena,
  fecha de verificacion, borrado logico y bloqueo de acceso.
- `sessions`: hash del token de sesion, usuario y fecha de vencimiento.
- `progress`: XP y listas JSON de lecciones y niveles del Arcade completados.
- `lesson_results`: intentos, errores, categoria, estrellas, mejor resultado
  y puntos por usuario y leccion.
- `custom_lessons` y `lesson_overrides`: contenido personalizado asignado a un
  alumno y cambios globales sobre lecciones del catalogo.
- `custom_games` y `custom_game_results`: juegos asignados, sus elementos y
  intentos/resultados del alumno.
- `email_verification_tokens`, `password_reset_tokens` y tablas de intentos y
  solicitudes: hashes y vencimientos para verificar, recuperar y limitar
  solicitudes de acceso/correo.

Las relaciones de usuarios, sesiones, progreso, lecciones y juegos usan claves
foraneas; los datos estructurados de listas y opciones se serializan como JSON
en columnas de texto. `server.js` crea el esquema al arrancar y aplica
migraciones incrementales para columnas incorporadas posteriormente.

El servidor crea/actualiza una copia SQLite en `registro_dos.db` al iniciar,
despues de respuestas exitosas a operaciones que modifican datos y cada cinco
minutos. La copia se realiza con la API de backup de `node:sqlite`; errores se
registran en la consola del servidor. `DATABASE_BACKUP_PATH` cambia la ruta.
Conserva ambos archivos fuera del control de versiones y usa almacenamiento
persistente al desplegar; una copia reciente no sustituye una estrategia de
retencion y restauracion probada.

12. PUBLICAR EN UN SERVIDOR Y USAR UNA URL PUBLICA
--------------------------------------------------

La direccion http://localhost:3000 solo funciona en la computadora que ejecuta
la aplicacion. Para que otras personas accedan por Internet, hace falta:

- Un proveedor de alojamiento que ejecute Node.js 22.13 o posterior.
- Un volumen de almacenamiento persistente para registro.db.
- Una URL publica y un certificado HTTPS valido.
- Un proxy inverso HTTPS, por ejemplo Caddy o Nginx, delante de Node.js.
- Configurar las variables de entorno de produccion y las credenciales SMTP en
  el panel seguro del proveedor de alojamiento.

En produccion, configura NODE_ENV=production, BASE_URL con la URL HTTPS publica
exacta, REQUEST_HASH_SECRET con al menos 32 caracteres aleatorios y las
variables SMTP. Para generar un secreto aleatorio puedes ejecutar:

node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"

No publiques ese secreto, las credenciales SMTP ni la contrasena del
superadministrador. El servidor usa por defecto `TRUST_PROXY=1`; en produccion
configuralo de acuerdo con la cantidad y topologia de proxies inversos
realmente confiables, en vez de asumir que siempre hay uno. Un valor incorrecto
puede hacer que el servidor interprete mal el protocolo o la IP del cliente.
No expongas directamente a Internet el puerto interno de Node si el proxy se
encarga de HTTPS.

Node.js 22.13 o posterior es el runtime previsto por el uso de `node:sqlite` y
`--env-file-if-exists`. `package.json` no declara una propiedad `engines`, por
lo que npm no impone por si solo esa version minima.

El volumen de la base de datos debe sobrevivir a los redepliegues. Si el
alojamiento tiene almacenamiento efimero, configura DATABASE_PATH para apuntar
a un volumen persistente. BASE_URL debe coincidir con la direccion HTTPS
publica para que funcionen los enlaces de confirmacion y recuperacion.

Subir el codigo a GitHub no crea una URL publica ni aloja la aplicacion. El
repositorio de GitHub es privado; la aplicacion aun debe desplegarse por
separado para tener una URL de Internet.

13. ARQUITECTURA Y ARCHIVOS PRINCIPALES
---------------------------------------

- `index.html`: punto de entrada y estructura de la interfaz; contiene los
  formularios de acceso, vistas del mapa y Arcade, aula docente y modales. Carga
  los scripts clasicos al final del documento en un orden que establece las
  funciones globales antes de `script.js`.
- `style.css`: estilos y diseno adaptable para pantallas grandes y moviles,
  mapa, modales, juegos, temas y estados de controles.
- `script.js`: estado principal del cliente y coordinacion de autenticacion,
  mapa, desbloqueo de contenido, lecciones, progreso, voz, efectos y los diez
  minijuegos del Arcade.
- `lesson-player.js`: utilidades de normalizacion/busqueda de texto y
  presentacion de resultados. El flujo de pasos de las lecciones esta en
  `script.js`, no en este modulo.
- `arcade-content.js`: bancos y funciones de seleccion aleatoria por nivel
  para el Arcade; puede usarse desde el navegador y desde las pruebas.
- `custom-games.js`: carga y ejecucion de juegos asignados por docentes:
  rompecabezas de palabras, memoria de parejas y puente de silabas.
- `teacher-dashboard.js`: panel de profesor/superadministrador, seleccion de
  alumnos, reportes, asignacion y edicion de lecciones y juegos.
- `emoji-catalog.js`: catalogo de imagenes emoji y terminos de busqueda usados
  al crear o editar actividades.
- `session-protection.js`: cierre por inactividad, pausa de descanso para
  alumnos, persistencia de ese temporizador en la pestana y comprobacion
  periodica de que la sesion siga valida en el servidor.
- `server.js`: servidor Express; API, sesiones, autorizacion por rol, correo,
  persistencia SQLite, copias de seguridad y publicacion controlada de recursos.
- `registro.db`: base de trabajo local configurada de forma predeterminada;
  contiene datos privados y se excluye de Git.
- `registro_dos.db`: copia de seguridad automatica configurada por defecto;
  tambien es privada y se excluye de Git.
- `test/server.test.js`: pruebas de integracion del servidor, autenticacion,
  autorizacion, lecciones, juegos, progreso y datos.
- `test/arcade-content.test.js`: pruebas de seleccion y coherencia de los
  bancos aleatorios del Arcade.
- `guia_de_colores_para_aprendizaje_infantil.txt` y
  `guia_de_elementos_visuales.txt`: recomendaciones de diseno; no todas las
  ideas de esas guias implican una funcion implementada.
- `package.json` y `package-lock.json`: comandos npm y dependencias con
  versiones fijadas. Las dependencias directas son Express y Nodemailer;
  SQLite se integra con Node.js.
- `.env.example`: plantilla de configuracion. Copiala a `.env`; nunca publiques
  `.env`, credenciales, cookies ni bases de datos reales.

La arquitectura es de cliente-servidor: el navegador dibuja la experiencia y
usa `fetch` con rutas `/api/...` para autenticacion y datos; Express valida y
autoriza esas operaciones y SQLite conserva la informacion. Los modulos del
cliente no son paquetes independientes: `index.html` los carga como scripts
globales, respetando su orden de dependencias. El servidor sirve archivos
estaticos mediante rutas previstas y responde 404 a rutas no publicadas; no
expone directamente el directorio del proyecto.

`script.js` mantiene el estado de interfaz de la sesion, el usuario, el mapa,
el progreso, la leccion activa y el contenido personalizado. Una parte del
estado de interfaz se guarda en `localStorage`; los datos de cuentas,
asignaciones e informes se obtienen del servidor. La vista previa docente
sustituye temporalmente el estado en memoria y evita guardar el progreso de
prueba.

La interfaz carga dependencias visuales externas desde CDN (Tailwind CSS,
Font Awesome, Google Fonts y Twemoji/jsDelivr). Tambien utiliza APIs del
navegador como SpeechSynthesis, Web Audio, canvas, drag-and-drop, temporizadores
y `fetch`. No hay service worker ni soporte offline implementado.

14. CONTENIDO ALEATORIO DEL ARCADE
----------------------------------

El Arcade tiene diez juegos, cada uno con tres niveles: Serpiente Lectora,
Ninja de Globos, Burbujas Parlantes, Tren de Silabas, Lluvia de Letras, Torre
de Bloques, Pincel Magico, Memoria Sonora, Carrera de Silabas y Pesca de Vocales.

Al comenzar una partida, las letras, silabas, palabras u opciones se eligen de
bancos adecuados al nivel. Las opciones de respuesta no se repiten; la respuesta
correcta se selecciona dentro del conjunto que el juego muestra. Tren y Torre
usan listas seleccionadas de silabas que forman palabras conocidas. Memoria
elige cuatro contenidos y crea dos cartas de cada uno. Lluvia presenta letras,
silabas o palabras segun el nivel. Al volver a jugar se vuelve a seleccionar
contenido aleatorio.

Para cambiar los bancos, edita arcade-content.js y conserva al menos cuatro
opciones por grupo, las palabras correctamente segmentadas y los tres niveles.
Despues ejecuta npm test. Los tests comprueban que las cartas siempre formen
cuatro parejas, las opciones no se repitan y los niveles invalidos se rechacen.

15. API Y DATOS
---------------

La interfaz usa el servidor local por HTTP y JSON. Las rutas principales son:

- **Autenticacion:** `POST /api/auth/register`, `/verify-email`,
  `/resend-verification`, `/login`, `/logout`, `/forgot-password` y
  `/reset-password`; `GET /api/auth/me` consulta la sesion.
- **Administracion (superadministrador):** `GET/POST /api/admin/users`,
  `PATCH /api/admin/users/:id/role`, `DELETE /api/admin/users/:id`,
  `POST /api/admin/users/:id/restore`,
  `PATCH /api/admin/users/:id/access` y
  `DELETE /api/admin/users/:id/sessions`.
- **Alumnos e informes (profesor o superadministrador):**
  `GET /api/teacher/students`, `/api/teacher/students/:id/experience` y
  `/api/teacher/students/:id/progress`.
- **Lecciones:** `GET /api/lessons/custom`, `/api/teacher/lessons`,
  `/api/teacher/lesson-overrides`, `GET /api/lessons/overrides`,
  `POST /api/teacher/lessons`, `PUT/DELETE /api/teacher/lessons/:id` y
  `PUT /api/teacher/lessons/catalog/:id`.
- **Juegos:** `GET /api/games/custom`, `GET/POST /api/teacher/games`,
  `DELETE /api/teacher/games/:id` y
  `POST /api/games/custom/:id/complete`.
- **Progreso:** `GET/PUT /api/progress`,
  `POST /api/progress/complete` y `/api/progress/reset`.

Las rutas de administracion exigen rol superadministrador. Las rutas
`/api/teacher/...` exigen profesor o superadministrador. Las rutas de progreso
y acceso del alumno requieren sesion; el registro publico solo crea alumno o
profesor. Las sesiones usan una cookie HttpOnly, SameSite=Lax y Secure en
produccion; el servidor guarda un hash del token aleatorio. Su vencimiento es
de siete dias y no se renueva en cada solicitud. Correo y contrasenas usan
tokens con vencimiento; la recuperacion invalida las sesiones existentes.

La API revisa el orden secuencial del catalogo y los niveles del Arcade para
alumnos, y permite saltos a profesores/superadministradores. Las lecciones
personalizadas deben pertenecer al alumno que solicita completarlas, aunque no
se ordenan en la secuencia del catalogo. Los resultados se calculan y escriben
en SQLite. El endpoint `PUT /api/progress` permite a una persona autenticada
actualizar su propio XP, pero rechaza cambios enviados a listas de lecciones o
niveles completados. El cliente comunica que una actividad fue completada; el
servidor no valida las respuestas individuales de la interfaz.

El esquema se crea en `server.js` e incluye las tablas `users`, `sessions`,
`progress`, `lesson_results`, `custom_lessons`, `lesson_overrides`,
`custom_games`, `custom_game_results`, `password_reset_tokens`,
`email_verification_tokens`, `verification_requests`,
`email_verification_attempts`, `password_reset_requests` y `login_attempts`.
Los hashes de correo, usuario e IP empleados para limitar intentos no son
valores de texto claro. Node.js incorpora SQLite mediante `node:sqlite`; no se
requiere instalar un servidor de base de datos adicional.

DATABASE_PATH y DATABASE_BACKUP_PATH pueden ser relativas a la carpeta del
proyecto o rutas absolutas. Para restaurar, deten el servidor antes de
reemplazar registro.db con una copia valida; no copies manualmente archivos
SQLite mientras el servidor esta escribiendo.

Las rutas estaticas publicadas por Express son explicitas: `/`, `/index.html`,
`/style.css` y los scripts del frontend. Las bases de datos, `.env`, el codigo
del servidor, `node_modules` y `test/` no se sirven como archivos publicos.

16. PRUEBAS Y CAMBIOS
---------------------

Ejecuta todas las pruebas con:

npm test

Las pruebas levantan un servidor aislado con una base temporal, comprueban
registro, verificacion por correo, inicio y cierre de sesion, permisos,
progreso, seguridad de rutas y contenido aleatorio. Los datos se eliminan al
terminar la prueba. Para revisar sintaxis del cliente:

node --check script.js
node --check arcade-content.js
node --check lesson-player.js
node --check custom-games.js
node --check teacher-dashboard.js
node --check session-protection.js
node --check server.js

`test/server.test.js` levanta una aplicacion con base temporal y transporte de
correo de prueba; `test/arcade-content.test.js` verifica seleccion aleatoria y
contenido de niveles. Al modificar interfaz, conserva el orden de scripts en
`index.html` y cambia el parametro de version de cache del recurso actualizado.
No cambies `package.json` sin actualizar `package-lock.json`.

17. SOLUCION DE PROBLEMAS
-------------------------

- No abre localhost:3000: confirma que npm start sigue ejecutandose, que estas
  abriendo la URL en la misma computadora y que el puerto no esta ocupado.
- No permite registrar o reenviar correo: comprueba BASE_URL, SMTP_HOST,
  SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_FROM y la carpeta de spam; reinicia
  el servidor despues de cambiar .env.
- No llega el codigo: verifica el correo, espera unos minutos, revisa spam y
  respeta los limites de solicitud; el codigo vence a los 10 minutos.
- Una cuenta existente no acepta la contrasena del administrador: cambiar
  ADMIN_PASSWORD solo afecta la creacion inicial; usa la recuperacion por correo.
- No se conserva la informacion tras un redepliegue: verifica que
  DATABASE_PATH apunta a un volumen persistente y que ese volumen sigue unido.
- No se puede iniciar sesion en otro navegador: usa la URL del mismo servidor,
  verifica el correo y comprueba que el hosting comparte la misma base de datos.
- No se ejecutan pruebas: confirma Node.js 22.13 o posterior con node --version
  y vuelve a instalar dependencias con npm install.

No guardes contrasenas, claves SMTP, tokens, cookies de sesion ni copias reales
de registro.db en Git. Para compartir el programa, comparte el codigo y una
plantilla de configuracion vacia; prepara credenciales y una base independiente
en el servidor de destino.
